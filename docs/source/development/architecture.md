# Architecture

Ultidock separates user commands, workspace management, molecular validation,
engine orchestration and result interpretation.

## Repository and generated workspace

| Location | Purpose |
| --- | --- |
| `pyproject.toml`, `requirements.txt`, `requirements-dev.txt` | Package metadata, runtime and developer Python dependencies |
| `cli/`, `ultidock/` | Public command entry points, installed package and workspace materialization |
| `molguard/io/`, `molguard/grids/`, `molguard/tests/` | Fixed-width molecular I/O, receptor prep, grid checks and regression tests |
| `docking/` | Setup, extraction, site/grid generation, engine dispatch, analysis and cleanup scripts |
| `benchmarks/` | DUD-E download/preparation, site recovery and active/decoy evaluations |
| `examples/` | Declared data and isolated example runners |
| `md-simulation/` | Protocols, selection, parameterization, GROMACS builders/runner, templates and tests |
| `data-analyses/` | Optional downstream notebooks and scoring audits |

Within an active application workspace, `docking/MACRO_MOL_DIR/` holds
receptors, grids and sites; `LIGANDS_DIR/` holds ligand archives and split
PDBQTs; `DOCKING_DIR/` holds raw poses; `ANALYSIS_DIR/` holds intermediate
analysis; `RESULTS_DIR/` holds SQLite and exports. `AUTODOCK_GPU_DIR/`
and `VINA_DIR/` locate native tools. `docking/config.py` is generated by
setup, and `docking/ligands.wget` is an optional download manifest.
For regular installs these paths are under the managed
`$XDG_DATA_HOME/ultidock` workspace, not in `site-packages`.

## Execution and persistence

The full pipeline performs setup, extraction, docking and analysis. Setup writes a
Python configuration consumed by legacy pipeline modules. Receptor preparation
precedes grid construction; worker jobs then combine receptor/site/ligand inputs.
Keep configuration mutations outside parallel job execution.

Setup creates directories idempotently, finds or builds AutoGrid and
AutoDock-GPU, and invokes shared MolGuard receptor preparation. Archive
download has retry behavior and can be skipped for local inputs;
`extract.py` uses `vina_split` to stage ligand PDBQTs. Grid generation
persists receptor/site metadata and reuses suitable maps instead of always
regenerating them. The bounded docking worker pool queues each discovered
ligand; each worker visits all prepared receptors and their sites. CUDA work
uses GPU device semaphores, while CPU mode runs Vina with configured threads.
GPU slots default to two per detected device and can be tuned with
`GPU_SLOTS_PER_DEV`.

MolGuard formats AutoDock numeric columns deterministically, rejects
invalid PDBQT records and checks generated maps for missing, all-zero or
nonfinite data. SQLite receives parsed docking records incrementally; the
analysis stage filters scored model rows for exports. If optional pandas
is unavailable, analysis warns and the docking results remain in SQLite.
The optional MD handoff selects current successful scored poses using the run
manifest, then requires reviewed protein/ligand chemistry and system inputs.
The shared receptor preparation implementation is
`molguard.io.receptor_prep`; production and benchmark paths use it rather
than separate receptor-conversion rules.

An installed package materializes scripts, example data and native build sources
in a managed writable workspace, rather than writing outputs into site-packages.
Source-checkout behavior and `ULTIDOCK_HOME` selection are covered by packaging tests.

## MD execution and provenance

`docking/run.py` records successful output identities/hashes and failures for
that invocation. Integrated MD restricts selection to that manifest, then
writes a sibling handoff status record. `md-simulation/poses.py` checks paired
GPU score/coordinate runs or Vina scored MODEL blocks. The protocol chooses
one receptor and engine, with a default of five distinct ligands.

Preparation snapshots reviewed inputs and selected poses in an MD job. The
runner validates immutable inputs, workflow identity and completed outputs,
builds each complex and executes GROMACS stages sequentially. Checkpoints
continue an unchanged TPR with append semantics. Dynamics stage budgets come
from protocol `threads`; the docking worker/GPU pool does not control MD.
MD trajectories and state remain in `md-simulation/workspace/` rather than
SQLite. See [MD execution](../user-guide/molecular-dynamics/running-and-results.md)
and [MD validation](md-validation.md).

## Documentation build

The Read the Docs tutorial-template layout keeps Sphinx sources in `docs/source/`
and generated output in `docs/build/`. The root `index.rst` supplies navigation;
Sphinx reads the Markdown guides through MyST without importing the scientific
runtime. `.readthedocs.yaml` installs only `docs/requirements.txt` and selects
`docs/source/conf.py`. Add new pages to the appropriate toctree in
`docs/source/index.rst` or its nested guide indexes. `docs/Makefile` and
`docs/make.bat` provide the template's local build commands.
